# 小红书矩阵内容协作工作台设计规格

## 目标

把现有“区域获客工作台”前台收敛为与用户真实经历直接相关的“小红书矩阵内容协作与质量工作台”。保留已经实现的 AI 生成、资料引用、事实核查、版本留痕、人工处理、失败恢复和导出能力，但降低第一次使用时的理解成本，让用户能在 3 分钟内完成一次可解释的内容协作演示。

## 设计判断

当前系统的后端和质量边界已经具备作品展示价值，主要问题是前台同时暴露了过多工程概念，且“区域教育/线索”叙事盖过了用户的小红书矩阵经历。因此本次不是重做 Agent，也不是继续扩展模块，而是做“前台信息架构减法 + 业务定位纠偏”。

## 用户与场景

### 主要用户

- 内容策略/运营负责人：提出需求、确认账号定位、审核内容和决定交付。
- 内容协作者/兼职/外部供应方：查看需求、提交稿件、根据意见修改。
- 面试观察者：通过一条真实可解释的案例理解业务、AI、人工判断和工程边界。

### 核心工作痛点

- 多账号、多选题、多稿件并行时，需求和交付状态容易丢失。
- 外部交稿质量不稳定，SOP 难以落实到逐条检查。
- AI 会把未经支持的表达写成确定事实，人工难以快速定位和处理。
- 修改会覆盖原稿，无法说明谁改了什么、为什么改。
- 发布后的问题没有沉淀为下一轮内容策略。

## 产品定位与命名

- 产品名：小红书矩阵内容协作工作台。
- 一句话说明：从内容需求到交付复盘，统一管理账号、资料、AI 初稿、人工审核和版本证据。
- 默认叙事：小红书矩阵内容协作，不以区域教育、直播或虚构线索作为首屏主场景。
- 历史经历内容只能标记为“历史项目自述/方法来源”，不能转写成平台通则、已验证指标或新的业务成果。

## 信息架构

一级入口控制在 4 个以内：

1. **工作台**：今日待处理、当前任务、主操作入口。
2. **内容任务**：全部任务、筛选、搜索和任务创建。
3. **内容与账号**：账号档案、资料台账、可复用内容和交付模板。
4. **复盘**：发布记录、问题归因、下一轮内容建议。

以下能力保留但降为二级入口，不再占据一级导航：

- AI 案例回放：位于任务详情的“过程与证据”。
- 质量评测：位于稿件详情的“发布前检查”，历史运行评测放在复盘的“系统记录”。
- 线索分拣：只有存在真实咨询记录时显示，默认不制造或填充线索。
- 模型连接、运行日志和技术状态：放入设置/系统状态区域。

## 首页结构

首页只回答三个问题：现在有什么需要处理、打开哪个任务、下一步做什么。

### 顶部区域

- 产品名与当前工作空间。
- 一个主按钮：`＋ 新建内容任务`。
- 次级按钮：`导入现成稿件`。
- 模型状态不作为主视觉，只在需要运行 AI 时提示。

### 待处理摘要

最多显示三项：

- 待补充资料/需求。
- 待审核稿件。
- 待交付内容。

不再同时展示大量统计卡、运行数、报告数和技术计数。

### 当前任务列表

每项只展示：标题、账号、内容目标、当前阶段、最新版本、下一步按钮。虚构演示内容不能与真实或历史素材混在默认列表；如保留体验入口，应单独标记为“演示模式”。

## 标准任务流程

任务详情采用单页五阶段时间线，用户始终知道自己在哪里以及下一步是什么。

### 1. 需求卡

字段：内容目标、目标受众、账号、内容形式、交付要求、截止时间、补充说明。

原“任务单”改成用户可理解的“需求卡”。资料不足时先提出问题，不直接生成看似完整的内容。

### 2. 账号与资料

显示当前账号定位、可用资料、资料来源等级、核验状态和有效期。用户可以补充资料，但不能静默替换已经被历史稿件引用的正文。

### 3. AI 产出

显示选题、标题、正文、封面和分页结果。默认只显示业务结果；“AI 使用了哪些资料、执行了哪些检查、发生了哪些失败重试”收进可展开的过程面板。

### 4. 审核与修改

审核意见按“必须修改 / 建议优化 / 已有依据 / 待人工确认”分组。每条意见都能定位到原文或标记为不可定位；人工处理只追加决定和理由，不能删除模型意见，也不能把人工处理冒充为准确率证明。

修改默认生成新版本，支持按字段或选区修改，锁定字段保持不变。用户可查看版本差异并重新运行静态质检。

### 5. 交付与复盘

交付前展示正文、封面、分页、标签、版本说明、未处理风险和当前审核状态。发布后可选填公开链接、曝光、收藏、评论和有效咨询；没有真实数据时保持空白，不生成演示指标。

## AI 能力呈现

内部保留四类职责，但前台统一称为“内容协作助手”：

- 需求澄清：发现地区、账号、受众、资料或交付目标缺失时先提问。
- 内容生产：基于选定资料和账号边界生成选题、图文稿和分页。
- 证据核查：逐句检查来源、引用范围、夸大承诺、时效和账号适配度。
- 反馈改稿：根据具体审核意见生成新版本，遵守锁定字段和选区范围。

每次 AI 操作都需要保存模型、提示词/工具版本、脱敏输入、资料范围、失败请求和结果摘要；不得保存或展示模型隐性推理文本。没有模型凭据时，界面明确显示“模型待配置”，不提供伪造的成功状态。

## 后端与数据策略

沿用现有 Node HTTP + SQLite + 原生前端，不引入新的服务框架或外部数据库。以下实体继续作为内部事实源：accounts、sources、tasks、drafts、runs、reviews、issueDecisions、publication、leads、evaluations。

前台只新增显示层的阶段映射，不重写旧实体：

- `ready`/`needs_input` → 需求与资料。
- `in_progress` → AI 处理中。
- `needs_review`/`changes_requested` → 审核与修改。
- `accepted`/`delivered` → 交付。
- 发布记录 → 复盘。

旧记录、旧稿件、历史运行和评测文件全部保留；演示资料、历史项目自述和真实材料必须在 UI 上有明确标签。

## 错误与边界

- 缺少资料：创建澄清问题，不生成政策、学校、账号或家长事实。
- 模型失败：保存失败运行和已知用量，允许安全重试；已有结果稿只重新审核，不重复生成。
- 引用无法定位：标为不可定位意见，不作为硬阻断依据。
- 未处理阻断问题：不能进入人工采纳或交付。
- 没有真实发布数据：复盘字段保持空白，不能显示虚构效果。
- 没有模型凭据：仍可浏览已有任务、稿件、质量结果和案例回放，但不能声称实时 AI 可用。

## 面试展示路径

控制在 3 分钟，使用一条已保存且明确标注证据边界的案例：

1. 展示一个矩阵内容需求和账号定位。
2. 选择资料，说明系统为什么不允许模型脱离资料作答。
3. 展示 AI 初稿和逐句核查。
4. 选中一条被扩大表达的事实问题。
5. 展示人工处理、锁定字段、版本差异和重新质检。
6. 导出交付稿，并说明发布数据和真人采纳仍需真实发生后补录。

面试重点不是“模型写得多快”，而是展示：如何把 AI 放进真实内容协作流程、如何防止错误进入交付、如何保留人工判断和可追溯证据。

## 明确不做

- 不把本作品包装成真实小红书平台数据系统。
- 不接入未经授权的私信抓取、自动发布或个人信息采集。
- 不把历史自述中的比例、线索、GMV或粉丝数据写成当前系统效果。
- 不继续增加一级导航、指标卡或 Agent 名称来制造复杂度。
- 不为了填充空态创建虚构账号、家长线索、学校政策或业务结果。

## 验收标准

- 新用户在 10 秒内能说出系统是“小红书内容协作工作台”。
- 从新建任务到导出稿件最多经过五个清晰阶段。
- 一级导航不超过四个。
- 每个阶段只有一个主操作和一个明确下一步。
- 复杂 AI 证据可展开查看，但不阻塞日常操作。
- 演示案例可在 3 分钟内完整讲完，且能回答来源、版本、失败、人工审核和数据边界问题。
- 现有自动化测试、数据库兼容和真实历史记录不回退。
- 桌面和 390px 移动端均无横向溢出，关键任务按钮可访问。
